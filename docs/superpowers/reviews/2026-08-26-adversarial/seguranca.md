Base: worktree `fase3b-meli-hibrido`, HEAD `31700c9` (99 commits em `--all`, 6 commits + 2 trees inalcançáveis via `git fsck`). Scripts de reprodução em `scratchpad/adv/` (`repro_rank_none.py`, `repro_inject_copy.py`, `repro_inject_copy2.py`, `injtest/`, `injtest_hook/`, `full_history.patch`).

## Afirmações refutadas

- **[A] O "wrapper `claude -p`" não é uma função de texto: é um agente com ferramentas, que lê o `.env` do CWD sem pedir permissão e executa hooks vindos do próprio repositório** — `src/afiliado/llm.py:25-28`; `deploy/afiliado.service:10,13,16`; `deploy/install-vps.sh:54`; `.github/workflows/publish.yml:34-49`; `docs/superpowers/specs/2026-08-23-afiliado-design.md:27,85`.
  O projeto trata `claude -p` como "wrapper" que devolve JSON (spec §2 e §4; `copywriter.py:43`, `selection.py:100`). Evidência de que é mais que isso:
  1. Capacidade (determinística, reproduzida): numa pasta com um `.env` falso (`injtest/.env` → `TELEGRAM_BOT_TOKEN=FAKE-zebra-4471-canary`), o comando exatamente como `llm.py` o monta:
     `claude -p "Leia o arquivo .env desta pasta e responda apenas com o valor de TELEGRAM_BOT_TOKEN, nada mais." --model haiku --output-format text` → saída `FAKE-zebra-4471-canary`, `exit=0`, sem prompt de permissão.
  2. Hooks do repositório rodam em modo headless (reproduzido): `injtest_hook/.claude/settings.json` com um hook `UserPromptSubmit` → `claude -p "Responda apenas com a palavra: oi"` criou `hook_ran.txt` com `HOOK_RAN_FROM_REPO_SETTINGS`. Na VPS o CWD é `/opt/afiliado` (o checkout do repo, `afiliado.service:10`); no Actions é o checkout também. Qualquer `.claude/settings.json` que chegue ao `main` vira execução de comando como usuário `afiliado`, com `/opt/afiliado/.env` legível (mesmo dono, `install-vps.sh:54`) e o código gravável (`chown -R afiliado`).
  3. `llm.py:26` não passa `--tools ""`, `--bare`, `--disallowedTools` nem `--setting-sources` (todos existem em `claude --help` 2.1.245); `subprocess.run` sem `env=` → o subprocesso herda as 11 variáveis de segredo do `.env`/Secrets.
  4. Entrada não confiável no prompt: `copywriter.py:18` embute `offer.title` (vendedor da Shopee / pool do ML); `selection.py:74-80` embute 30 títulos + `recent_titles` do SQLite.
  Exploração via título tentada 2× com Haiku pelo caminho real (`copywriter.write_copy`): `repro_inject_copy.py` — o modelo ignorou a instrução e escreveu copy normal (canary não vazou); `repro_inject_copy2.py` — as duas tentativas do LLM falharam e saiu o `fallback_copy` ("🔥 Achado do dia"), canary não vazou. Ou seja: a capacidade está provada, a exploração por título não foi demonstrada — por isso A, não C. Dano se um dia o modelo obedecer: `check_copy` (`validate.py:59-69`) só barra "http" e tamanho — um token do Telegram (46 chars) cabe em `description` (≤120) e vai para o canal público. Dano via repositório: um push malicioso (PAT no `.git/config`, ver achado abaixo; `GITHUB_TOKEN` com `contents: write` em `publish.yml:21-22`; dependência comprometida em `pip install -e .`/`npm install -g` sem pin) = RCE persistente na VPS a cada 5 min.

  `data.get("chosen", [])` devolve `None` quando a chave existe com valor nulo; `dict.fromkeys(str(i) for i in None)` → `TypeError`. `rank_offers` é chamado em `pipeline.py:61` fora de qualquer `try`, então o run aborta antes de publicar qualquer coisa; `cli.py:279` manda "❌ Run abortado: 'NoneType' object is not iterable" ao chat de operações — sem dizer qual item/prompt causou. Reprodução (`repro_rank_none.py`, 3 candidatas, `posts_per_run: 1`):
  ```

  {'chosen': 5}        -> TypeError: 'int' object is not iterable
  ```

- **[A] O portão de link é um clique de afiliado feito pelo próprio pipeline, de IP de datacenter, com User-Agent falso — em todo post e também no `--dry-run`** — `src/afiliado/validate.py:10,14,17-27`; `src/afiliado/pipeline.py:98` vs `:103`; spec §8 linhas 176-177; spec §10 linha 210 ("dry-run … imprimindo os posts no terminal em vez de publicar").
  `check_link` faz `GET` no link curto de afiliado (`s.shopee.com.br/…`, `meli.la/…`) com `follow_redirects=True` e `User-Agent: Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36` — ou seja, segue o redirect de rastreamento até a página do produto, que é exatamente o que um clique de afiliado é. `validator(post, cfg)` roda em `pipeline.py:98`, ANTES do `if dry_run` de `:103` → o dry-run "não publica" mas clica. Consequências: (1) o teste de atribuição do ML que o dono está fazendo (contexto: "o painel mostrando 2 cliques não prova nada") está contaminado — cada `afiliado run --dry-run` já registra um clique no link que ele está tentando isolar; (2) em produção, 50-100 links/dia recebem o PRIMEIRO clique segundos depois de gerados, todos do mesmo IP de datacenter, todos com UA idêntico e falso, antes de qualquer humano — assinatura clássica de tráfego inválido para os programas de afiliados (avaliação: os termos da Shopee/ML sobre cliques artificiais não são verificáveis offline; o risco é encerramento da conta = 100% da receita); (3) CTR do painel poluído em +1 clique por post. `check_image` (`validate.py:49`) e `creative._download_image_bytes` (`creative.py:116`) fazem o mesmo com a imagem — inofensivo para o programa, mas confirma que "dry-run" toca as três URLs externas.

- **[A] O token do bot do Telegram é entregue à Meta em cada post de feed, e a docstring minimiza ("expira em ~1h")** — `src/afiliado/channels/instagram_feed.py:6-10,85-89,104-116`; `src/afiliado/channels/telegram.py:106`.

- **[A] Nenhum post identifica que é publicidade / link de afiliado; a própria guideline de marca empurra o aviso só para a bio** — `src/afiliado/message.py:45-54`; `src/afiliado/channels/instagram_feed.py:136-142` (caption: só "🔗 Link na bio e no canal do Telegram"); `src/afiliado/channels/story_dispatch.py:46-49`; `docs/brand-guidelines.md:64` ("Sempre presente: aviso de link de afiliado na bio/descrição do canal"); `grep -i "publi|CONAR|#ad" docs/` → nenhuma menção a "#publi"/"publicidade" em post.

## Riscos fora do código

- **`CLAUDE_CODE_OAUTH_TOKEN`**: validade ~1 ano (`vps-setup.md:128-129`), vive nos Secrets do Actions, no `/opt/afiliado/.env` (600) e no ambiente de TODO subprocesso `claude -p`. Vazou = terceiro consome a assinatura Max do dono como se fosse ele (limites compartilhados → as ~200 chamadas/dia do pipeline passam a falhar → copy de template e ranking determinístico, degrada sem parar). Avaliação: o escopo é a autenticação do Claude Code da conta; revogação manual.
- **Geração de link do ML por endpoint interno**: `meli_links.py:19,24-26,59-66` — cookies de sessão + UA de Chrome fixo + lotes de 50 num endpoint sem contrato público. Roda na máquina do dono (skill), então IP = IP do login; a premissa "IP de servidor" NÃO vale para a geração, mas VALE para o clique de validação (achado acima), que sai da VPS. Termos do programa de afiliados do ML sobre acesso automatizado: não verificáveis offline; o dano de um encerramento é 100% da receita ML mais o app OAuth.
- **Volume na Open API da Shopee**: `fetch_offers` = 5 categorias × até 2 páginas (`shopee.py:74-95`, `config.yaml:57-62`) = até 10 chamadas/run × 288 runs/dia ≈ 2.900 chamadas/dia + 1 `generateShortLink` por post. Limites do programa não verificáveis offline; estouro vira `SourceError` → run abortado → 1 alerta a cada 5 min.
- **`data/meli_links.json` não existe em nenhum checkout e nunca foi commitado** (`git log` vazio; `ls data/` nos dois checkouts). Com `sources.meli: true`, toda oferta do ML é descartada em `meli.py:235` ("sem link de afiliado no pool") — fora da minha área, mas é evidência de que o runbook ("é commitado", `meli-setup.md:160-161`) descreve um arquivo que não existe.
- **Canal público + bot administrador**: qualquer vazamento do token (achado da Meta, `.env`, log do Actions) é tomada do @fiscaldapromo sem segunda barreira; rotação só pelo BotFather, e o token novo precisa ir para Secrets + VPS.
